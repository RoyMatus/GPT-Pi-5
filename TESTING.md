# Проверки GPT-Pi 5

Выбирать проверки по изменённому поведению, а не запускать всё после каждой правки.
Успешные результаты сохраняют силу, пока относящиеся к ним код, зависимости,
конфигурация и среда не изменились. Проверка должна обнаруживать реальную ошибку,
а не повторять реализацию или фиксировать формулировки документации.

| Изменение | Минимальная проверка |
| --- | --- |
| README/инструкции | Diff, локальные ссылки, согласованность RU/EN; без запуска приложения |
| Навыки/профили | `python tools/check_guidance.py`, проверка сценариев применения |
| GitHub-инструменты | `python -m unittest discover -s tests -p test_github_tools.py -v` |
| Диагностика устройства | `python -m unittest discover -s tests -p test_execution_profile.py -v` |
| Домен/сессии | Соответствующие offline-тесты, отрицательные сценарии доступа |
| HTTP/хранилище/авторизация | Позитивные и негативные интеграционные тесты, смена/истечение сессии |
| UI/голос/автозапуск | Автоматизируемые контракты + целевой экран/звук/загрузка на Pi |
| Общие зависимости/упаковка/сквозные изменения | Полный offline-набор и проверка пакета |

Для приложения установить `PYTHONPATH=src` (PowerShell: `$env:PYTHONPATH='src'`).
Windows sensor fixtures: `python -m unittest discover -s tests -p test_windows_sensors.py -v`.
Без драйверов/сети проверяются CSV/N/A/ranges, MiB→bytes, выбор CPU Package/core
clock, срок/повреждение cache и повторная атомарная публикация в PowerShell 5.1.
Проверка упаковки проходит и на Linux; PowerShell-тесты там пропускаются.
Доступ к физическим CPU/GPU, ACL задачи и реальный SSH проверяются отдельно на ПК/Pi.
Перед установкой приложения собрать интерфейс: `npm ci`, затем `npm run build`.
В venv выполнить `python -m pip install .`; зависимости приложения обязательны.
Полный набор: `python -m unittest discover -s tests -v`.
Голосовой клиент: `node --test tests/voice.test.mjs` (также `npm test`).
Проверка упаковки: `python -m pip wheel . --no-deps -w dist`.
Python 3.11+; инструменты работают из корня репозитория без runtime-зависимостей.

В v0.2 тесты test_cloud.py проверяют OAuth/ID token и транспорт с MockTransport;
test_webapp.py проверяют реальные HTTP-границы через ASGI TestClient, включая
чужие ID, CSRF, logout во время генерации, истечение и restart. Возврат из OAuth
проверяется с cross-site Fetch Metadata всей цепочки перенаправлений; исключение
для главного document не должно разрешать cross-site API, iframe или POST. Токены и ответы
в этих тестах синтетические. Автоматическое открытие auth.openai.com может
встретить защитную страницу; оно не заменяет ручной вход владельца.
test_remember_login.py проверяет сохранение после простоя/restart, восстановление
только по своей cookie и регистрации, logout, ротацию refresh, временную сеть,
терминальный отказ и блокировку второго процесса. Переписка не сохраняется.
`python tests/browser_remember_login.py` проверяет постоянный профиль Chromium,
обновление открытой страницы после restart, сохранение после перезапуска браузера
и отсутствие восстановления после явного выхода. Облако синтетическое.
Для UI проверять 1280×800, целевой 720×1280 и узкий 390×844, светлую/тёмную тему,
модели, отправку, отмену, выход и отсутствие ошибок браузера. Playwright —
необязательный инструмент разработки, не зависимость устройства.
Для повторения браузерных сценариев CI после сборки/установки приложения:

```sh
python -m pip install playwright==1.65.0
python -m playwright install chromium
python tests/browser_voice.py
python tests/browser_remember_login.py
```

На Ubuntu CI устанавливает Chromium с `--with-deps`. Оба сценария используют
временный каталог, синтетический аккаунт и FakeCloud; переход на auth.openai.com
перехватывается браузером, реального OAuth/ответа облака нет. Голосовой сценарий
подменяет микрофон Chromium и STT/TTS через FakeVoice; модели Vosk/Piper не устанавливаются.

test_voice.py проверяет PCM-формат/размер, аутентификацию, CSRF/Origin, отмену,
logout с поздним результатом и завершение рабочего процесса. Клиентские тесты
проверяют PCM и позднее разрешение микрофона после отмены. Для браузера использовать
синтетический микрофон и fake STT/TTS: запись → текст → отправка → звук → выход.
После установки необязательного Playwright и Chromium: `python tests/browser_voice.py`.
Сценарий также запрещает позднее озвучивание скрытой страницы; реальный микрофон
и облако в нём не используются. Браузер/аудиоправа проверяются отдельно на Pi.
Он также проверяет гостевые кнопки аудио, закрытие/скрытие во время записи,
ошибку отсутствия микрофона/динамика и запрещает enumerateDevices: на проверенном
Pi этот вызов открывал лишний системный запрос камеры. test_audio_devices.py
проверяет исключение Dummy Output/мониторов, отсутствие зависимости от USB-ID,
неизвестное состояние при недоступности PipeWire. API отдаёт только два признака,
не идентификаторы, имена устройств, список клиентов или данные записи.
На Pi отдельно проверить локальные движки синтетической фразой, затем реальный
USB capture/playback. Успех синтетического цикла не подтверждает исправность кабеля,
микрофона, динамика или удобство/точность распознавания живой речи.

## Работа с тестами

Для нового проверяемого поведения/воспроизводимого бага: написать минимальный
сценарий, увидеть ожидаемое падение именно по причине поведения, реализовать,
затем проверить зелёный результат. Ошибка среды/импорта не доказывает воспроизведение бага.
Для рефакторинга достаточно зелёной исходной проверки и недостающих characterization
тестов. Для документации/субъективного дизайна/живого оборудования применять
соответствующую проверку и объяснять ограничение; не придумывать RED задним числом.

Облако заменяется fake-транспортом. CI не использует API-ключи, настоящие чаты,
микрофон, SSH и платные запросы. Тесты инструментов не создают issues/PR в GitHub.
Синтаксис/ссылки навыков не доказывают качество решений агента: для сложных навыков
проверить также реалистичные сценарии из docs/AI_WORKFLOW.md.

## Платформы и выпуск

Текущая матрица Actions: Windows/Linux, Python 3.11/3.13, Node.js 22.
Отдельный обязательный job `browser` на Ubuntu 24.04/Python 3.13 запускает оба
синтетических сценария Chromium. Матрица ограничена 15 минутами на job,
браузерный job — 20 минутами, каждый браузерный сценарий — пятью минутами.
Actions закреплены полными SHA; их Node.js 24 runtime не меняет Node.js 22 приложения.
GitHub Actions разрешены.
При изменении имен jobs согласовать EXPECTED_CHECKS в tools/github_api.py.
Результат CI не подтверждает работу на ARM64, качество звука, тач и автозагрузку.
Перед выпуском на устройство выполнить выбранные аппаратные сценарии на Pi:
гостевой старт без cookie и восстановление сохранённого входа, отключение сети, остановка записи/озвучивания
при выходе, отсутствие ответа другого профиля, restart и восстановление после питания.
Не объявлять выпуск проверенным при недоступном обязательном оборудовании.

## Доказательства

Фиксировать конкретный коммит/состояние, платформу, команды, результат и ограничения.
Не складывать времена параллельных задач в «общее время»; неизвестное не оценивать
по датам коммитов. Логи хранить в игнорируемом build/ без секретов и личных данных.
Один владелец координирует проверки на устройстве и интеграцию работы агентов.

Dashboard contracts: `node --test tests/dashboard-foundation.test.mjs`. This verifies cancellation, single-producer subscriptions and timezone midnight behavior, not visual or hardware acceptance.

Shell matrix: `python tests/browser_dashboard_foundation.py` (optional `--browser-channel msedge`). Voice/login runners accept optional `GPT_PI_TEST_BROWSER_CHANNEL=msedge` for local Windows checks; CI uses Chromium. Tab transitions during recording/playback are included in browser_voice.py.

Dashboard: Python `test_dashboard*.py`, Node `dashboard-calendar.test.mjs` и
`dashboard-foundation.test.mjs`. Браузерные сценарии browser_dashboard_{overview,
computer,markets,calendar,photos}.py используют только синтетические источники;
общая подмена исключает live providers при переходах между вкладками.


## Полноэкранная клавиатура и настройка Windows SSH

`test_keyboard.py` проверяет безопасное чтение геометрии (TTL, размер, тип,
владелец/права/ссылки), отсутствие текста в ответе и гостевой endpoint.
`test_osk_overlay.py` при наличии Linux C/GLib собирает изолированный GObject
harness: только поверхность osk в squeekboard меняет слой. Другие процессы и
поверхности не затрагиваются. Пропуск на Windows не заменяет ARM64-проверку.
`browser_dashboard_computer.py` проверяет свободную область при клавиатуре,
видимость поля, DPR 2, клики при blur и восстановление высоты после скрытия.

`test_windows_setup.py` запускает только безопасный preview без повышения прав
или установки службы; проверяет отказ для внедрённых ключевых опций/строк и
неподходящих адресов. Реальная установка Windows Capability, ACL, firewall и
forced-command проверяются отдельно на разрешённом ПК после UAC. В CI этих
системных изменений нет. На Pi отдельно проверять kiosk после перезагрузки,
появление клавиатуры, синтетическую экранную букву и видимость composer над ней.

`test_windows_collector.py` проверяет сохранение причины Failed job и освобождение job, а также получение CPU/RAM/диска при полностью недоступном CIM provider. Штатные IP byte counters и uptime не требуют внешнего запроса или дополнительных групп. Реальный источник проверять отдельно через закреплённый SSH-ключ и авторизованный browser-сеанс.

## Графические схемы

После `npm run build` выполнить `node tests/browser-themes.mjs`. Сценарий использует
собранный интерфейс с синтетическими ответами вместо backend; реальный аккаунт,
облако и внешние источники не нужны. Проверяются все 15 схем, шесть вкладок на
трёх размерах, портальные диалоги, контраст с учётом alpha-композиции,
сохранение после перезагрузки, миграция прежнего `fluent` в светлую/тёмную схему
и отказ браузерного хранилища. Ожидаемое падение до реализации и результаты
после неё фиксировать отдельно, не выводить их из наличия теста.

Нужен необязательный Node-модуль Playwright из среды разработчика. Если он не
находится обычным разрешением модулей, `GPT_PI_PLAYWRIGHT_PATH` задаёт путь к нему;
`GPT_PI_TEST_BROWSER_CHANNEL` выбирает установленный канал браузера, например `msedge`.
Это инструменты разработки, не новые зависимости устройства.

`npm test` включает `tests/appearance.test.mjs`: миграция предпочтений, отказ
хранилища и контраст мелкого текста записи. Рендеры и галерея собираются командой
`node tools/render-theme-gallery.mjs --dir build/fluent-theme-renders`; нужен необязательный Sharp (обычный импорт
или `GPT_PI_SHARP_PATH` к существующему модулю). Изображения и `verification.json`
сохраняются в игнорируемом каталоге, в Git входят только исходники генераторов.

Рендеры в `build/fluent-theme-renders/` показывают реальный UI с синтетическими погодой,
котировками, телеметрией и сообщениями. Для каждой схемы проверять шесть вкладок,
экран входа, настройки, диалоги и управление фото; сохранять проверки контраста,
переполнения и сенсорных размеров. Отдельно проверять доступность всех действий
после раскрытия дополнительных настроек ПК, рынков, фото и даты отсчёта, а также
непрозрачный fallback, reduced-transparency/forced-colors, фокус и текст 200%.
В Green Phosphor статус и знак изменения должны читаться без красного цвета.
Субъективная оценка, полная доступность, физический экран и производительность GPU Pi
не подтверждаются одним набором снимков и требуют отдельной приёмки.
