# Проверки GPT-Pi 5

Выбирать проверки по изменённому поведению, а не запускать всё после каждой правки.
Успешные результаты сохраняют силу, пока относящиеся к ним код, зависимости,
конфигурация и среда не изменились. Проверка должна обнаруживать реальную ошибку,
а не повторять реализацию или фиксировать формулировки документации.

| Изменение | Минимальная проверка |
| --- | --- |
| README/инструкции | Diff, локальные ссылки, согласованность RU/EN; без запуска приложения |
| Навыки/профили | `python tools/check_guidance.py`, проверка сценариев применения |
| GitHub-инструменты | `python -m unittest discover -s tests -p test_github_tools.py -v` |
| Диагностика устройства | `python -m unittest discover -s tests -p test_execution_profile.py -v` |
| Домен/сессии | Соответствующие offline-тесты, отрицательные сценарии доступа |
| HTTP/хранилище/авторизация | Позитивные и негативные интеграционные тесты, смена/истечение сессии |
| UI/голос/автозапуск | Автоматизируемые контракты + целевой экран/звук/загрузка на Pi |
| Общие зависимости/упаковка/сквозные изменения | Полный offline-набор и проверка пакета |

Для приложения установить `PYTHONPATH=src` (PowerShell: `$env:PYTHONPATH='src'`).
Полный набор: `python -m unittest discover -s tests -v`.
Проверка упаковки: `python -m pip wheel . --no-deps -w dist`.
Python 3.11+; инструменты работают из корня репозитория без runtime-зависимостей.

## Работа с тестами

Для нового проверяемого поведения/воспроизводимого бага: написать минимальный
сценарий, увидеть ожидаемое падение именно по причине поведения, реализовать,
затем проверить зелёный результат. Ошибка среды/импорта не доказывает воспроизведение бага.
Для рефакторинга достаточно зелёной исходной проверки и недостающих characterization
тестов. Для документации/субъективного дизайна/живого оборудования применять
соответствующую проверку и объяснять ограничение; не придумывать RED задним числом.

Облако заменяется fake-транспортом. CI не использует API-ключи, настоящие чаты,
микрофон, SSH и платные запросы. Тесты инструментов не создают issues/PR в GitHub.
Синтаксис/ссылки навыков не доказывают качество решений агента: для сложных навыков
проверить также реалистичные сценарии из docs/AI_WORKFLOW.md.

## Платформы и выпуск

Текущая матрица Actions: Windows/Linux, Python 3.11/3.13. GitHub Actions разрешены.
При изменении имен jobs согласовать EXPECTED_CHECKS в tools/github_api.py.
Результат CI не подтверждает работу на ARM64, качество звука, тач и автозагрузку.
Перед выпуском на устройство выполнить выбранные аппаратные сценарии на Pi:
старт в заблокированном состоянии, отключение сети, остановка записи/озвучивания
при выходе, отсутствие ответа другого профиля, restart и восстановление после питания.
Не объявлять выпуск проверенным при недоступном обязательном оборудовании.

## Доказательства

Фиксировать конкретный коммит/состояние, платформу, команды, результат и ограничения.
Не складывать времена параллельных задач в «общее время»; неизвестное не оценивать
по датам коммитов. Логи хранить в игнорируемом build/ без секретов и личных данных.
Один владелец координирует проверки на устройстве и интеграцию работы агентов.
